# Design Decisions

Живой документ. Каждое решение имеет номер, обоснование и последствия.
При изменении решения старый пункт не удаляется — добавляется новый
с пометкой "supersedes DD-XXX".

---

## DD-001. Детерминированная симуляция через единый источник времени

**Решение.** Всё время в симуляции — `VirtualTime` (u64 наносекунд от старта).
`std::time::{Instant, SystemTime}` в `dsfs-core` запрещены (кроме `#[cfg(test)]`).

**Обоснование.** Реальное время недетерминировано; любой его источник в движке
ломает воспроизводимость.

**Последствия.**
- Узлы не читают время, они получают `TimerFired { now }`.
- CI-grep проверяет отсутствие `Instant::now|SystemTime::now` в `dsfs-core/src/*.rs`
  (кроме тестов).

## DD-002. Порядок событий: `EventKey = (time, priority, seq)`

`BinaryHeap` в Rust нестабилен по отношению к равным элементам, а порядок
вставки при равных ключах — недетерминирован на уровне гарантий стандартной
библиотеки (зависит от истории операций). Чтобы порядок не зависел от этой
истории, ключ сортировки должен быть полным.

**Решение.** `EventKey { time: VirtualTime, priority: Priority, seq: EventSeq }`.

- `time` — виртуальное время.
- `priority` — класс события; при равном времени определяет семантический порядок.
- `seq` — монотонный счётчик регистрации события в `EventQueue`.

**Семантика `Priority`.** Меньшее значение = раньше обрабатывается при равном
`time`. Порядок между классами:

1. `Timer = 0` — истечение таймеров (election, heartbeat).
2. `Network = 1` — доставка сетевых сообщений.
3. `Client = 2` — клиентские запросы извне.
4. `System = 3` — внутренние события движка (метрики, random replies).

**Последствия.**
- `seq` монотонный и не переиспользуется.
- Тест: при N событиях с одинаковыми `(time, priority)` порядок обработки
  строго соответствует порядку регистрации.
- Изменение семантики `Priority` требует bump `SIM_VERSION`.

## DD-003. RNG: разделение потоков по StreamId

**Проблема.** Один глобальный RNG ломает локальность изменений: добавление
случайного вызова в одном модуле сдвигает поток и меняет поведение всех
остальных модулей.

**Решение.** Корневой seed (`master_seed: u64` из конфига) разворачивается
в независимые потоки `ChaCha8Rng`, по одному на `StreamId`.

**StreamId** — стабильный `u64`:

| Диапазон  | Назначение |
|-----------|------------|
| 0–99      | Сеть (0 = latency, 1 = loss, 2 = dup, 3 = reorder) |
| 100–999   | Raft per-node (100 + node_id*10 + purpose) |
| 1000–1999 | Fault injection |
| 2000+     | Резерв |

**Правила.**
- Номера существующих `StreamId` никогда не меняются — только добавляются.
- Каждый модуль создаёт свои `StreamRng` при инициализации и хранит их.
- Добавление нового `StreamId` не влияет на существующие потоки
  (`seed_i = mix(master_seed ^ stream_id_i)`).
- Изменение семантики использования `StreamId` = bump `SIM_VERSION`.

**Тест.** `consuming_one_stream_does_not_affect_another` в `rng.rs`.

## DD-004. Оффлайн-checker + онлайн-инварианты

**Решение.** Checker работает оффлайн на журнале (Vec<LogRecord> или JSONL).
Онлайн — только дешёвые инварианты (single-leader-per-term), O(1) на событие.

**Обоснование.** Свойства вроде «no lost committed entries» нельзя проверить
«в моменте» — только на полной истории.

**Последствия.**
- Каждое значимое действие узла/сети попадает в LogRecord.
- LogRecord содержит `event_id` и `caused_by: Option<EventId>` — строится DAG.

## DD-005. Правило регрессионных тестов

Каждый обнаруженный баг, приводящий к нарушению инварианта, фиксируется
отдельным тестом (`tests/regressions/<short-name>.rs`), который падал
до фикса и проходит после.

## DD-006. Duplication semantics

**Решение.** Дублирование сообщения моделируется как **вторая доставка в
тот же момент времени**, что и оригинал. Оба экземпляра помечаются в логе
(`MessageSent` для первого, `MessageDuplicated` для второго), и оба
регистрируются как отдельные `EventKind::MessageDelivered` в очереди.

**Обоснование.**
- Raft обязан быть идемпотентным; для него порядок «оригинал раньше
  дубля в тот же момент» определяется `EventSeq` (DD-002) — детерминирован.
- Раздельные времена доставки потребовали бы отдельного латентного
  решения для дубля, что усложнило бы per-link latency stream и снизило
  бы детерминизм (дубль мог бы прийти раньше оригинала).
- Реальные сети допускают и «раньше», и «позже»; для симулятора
  достаточно одного канонического варианта.

**Что теряем.** Не моделируем «дубль пришёл с большей задержкой» как
отдельный сценарий. Модель jitter на дубль не распространяется. Если
понадобится — добавим `duplicate_delay` в `LinkConfig`.

## DD-007. Loss vs. latency RNG ordering

**Решение.** При отбрасывании сообщения `loss_rng` потребляется, а
`latency_rng` — **нет**. Порядок решений: partition → loss → latency →
duplicate.

**Обоснование.** Если бы `latency_rng` потреблялся для потерянных
сообщений, то наличие потерь на одном канале сдвигало бы значения
латентности для всех последующих доставок **на всех каналах**. Это
нарушает принцип локальности изменений (DD-003): конфигурация одного
канала влияла бы на поведение другого.

Тест `loss_does_not_perturb_latency_stream` в `network.rs` фиксирует
это свойство.

**Цена.** Если пользователь поменяет `loss_probability` на лету, то
последовательность латентностей для выживших сообщений **не изменится**
относительно «без потерь» — это желаемое поведение.

## DD-008. Reordering through jitter, not shuffling

**Решение.** Переупорядочивание сообщений моделируется исключительно
через `LinkConfig.jitter`: задержка = `base + uniform(0, jitter)`. Когда
`jitter >= base`, соседние сообщения на одном канале естественно
приходят в разном порядке.

**Обоснование.**
- Перемешивание очереди «в полёте» потребовало бы хранить её в движке,
  что нарушает принцип «движок не имеет состояния, кроме часов и
  очереди событий».
- Детерминированный replay перемешанной очереди требует логирования
  каждого решения о перестановке — это раздувает лог и замедляет
  симуляцию.
- Физически reordering в реальных сетях — следствие разной задержки,
  а не самостоятельный процесс. Модель «перемешать» нефизична.

**Ограничение.** Не моделируем переупорядочивание при `jitter < base`.
Это соответствует реальности: при `jitter < base` порядок сохраняется.

## DD-009. `NetworkModel::deliveries` returns `Vec<Delivery>`, not `Option<VirtualTime>`

**Решение.** Интерфейс сети возвращает вектор доставок, каждая из которых
несёт время и флаг `is_duplicate`.

**Обоснование.**
- Дублирование (DD-006) невозможно выразить через `Option`.
- Будущие варианты (например, «частичная доставка broadcast-сообщения
  подмножеству получателей») тоже ложатся на `Vec` без смены интерфейса.
- Пустой `Vec` = потеря; один элемент = обычная доставка; два элемента
  = дубль. Единая семантика.

**Последствия.** `SimulationEngine::enqueue_message` обходит `Vec` и
регистрирует доставку для каждого элемента. Лог получает либо
`MessageSent` (первый), `MessageDuplicated` (последующие), либо
`MessageDropped` (пусто).
